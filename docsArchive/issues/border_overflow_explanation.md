# 边框文本溢出问题详解

## 问题现象

```
┌──────────────────────────────────────────────────────────────────────────────────────────────┐
│🌲 Render: Component functions called to generate new VNode trees based on current state.   │← 溢出
└──────────────────────────────────────────────────────────────────────────────────────────────┘
```

文本超出了右边框 1 个字符位置。

---

## 根本原因分析

### 1. 代码逻辑

```go
text := "🌲 Render: Component functions called to generate new VNode trees based on current state."
content := fmt.Sprintf("%-98s", text)  // ❌ 问题所在
```

**期望行为**：
- `fmt.Sprintf("%-98s", text)` 将文本填充到 98 字节宽度
- 文本应该刚好填满边框内部（100 屏幕 - 2 边框 = 98）

**实际行为**：
- 填充到 98 **字节**，而不是 98 个**字符位置**
- 导致实际显示宽度超过 98，溢出边框

---

### 2. 技术细节

#### 字节 vs 显示宽度

```
文本: "🌲 Render: Component functions..."

┌─────────────────────────────────────┬──────────────┬──────────────┐
│ 内容                                 │ 字节长度     │ 显示宽度     │
├─────────────────────────────────────┼──────────────┼──────────────┤
│ 原始文本                              │ 91 字节      │ 89 位置      │
│ emoji 🌲                              │ 4 字节       │ 2 位置       │
│ 其他字符                              │ 87 字节      │ 87 位置      │
└─────────────────────────────────────┴──────────────┴──────────────┘
```

#### fmt.Sprintf 格式化后

```
格式化: fmt.Sprintf("%-98s", text)

┌─────────────────────────────────────┬──────────────┬──────────────┐
│ 内容                                 │ 字节长度     │ 显示宽度     │
├─────────────────────────────────────┼──────────────┼──────────────┤
│ 格式化文本                            │ 101 字节     │ 99 位置 ❌   │
│ 填充空格 (7 个字节)                   │ +7 字节      │ +7 位置      │
│ 总计                                 │ 91 + 7 = 98  │ 89 + 7 = 96  │
│ + emoji 的多字节问题                 │              │ +3 位置 ⚠️   │
└─────────────────────────────────────┴──────────────┴──────────────┘
```

**等等，为什么是 99 而不是 98？**

关键问题：`fmt.Sprintf("%-98s", text)` 的逻辑：

1. 计算字符串的**字节长度** = 91 字节
2. 补充空格到 **98 字节**
3. 返回字符串：91 字节文本 + 7 字节空格 = 98 字节

**但是**，这 98 字节的**显示宽度**是多少？

- 文本内容（91 字节）的显示宽度 = 89 位置
  - 因为 emoji 🌲 占用 4 字节但只显示 2 位置
- 空格（7 字节）的显示宽度 = 7 位置
- **总显示宽度 = 89 + 7 = 96 位置**

等等，96 < 98，应该不会溢出啊？

让我重新检查...

---

### 3. 真正的问题

实际上，问题更复杂：

```go
fmt.Sprintf("%-98s", text)
```

这个函数：
1. **不是**填充到固定 98 字节
2. **而是**：如果字符串 < 98 字节，在右边补空格到 98 字节
3. 如果字符串 ≥ 98 字节，**返回原字符串不变**

但是我们的文本是 91 字节 < 98 字节，所以：
- 会在右边补 7 个空格
- 最终字符串：91 字节文本 + 7 字节空格 = 98 字节

但是实际显示宽度是：
- 91 字节文本 → 89 显示位置（因为 emoji）
- 7 字节空格 → 7 显示位置
- 总计：96 显示位置

96 < 98，理论上不应该溢出？

**让我再仔细测试一次：**

```go
text := "🌲 Render: Component functions called to generate new VNode trees based on current state."
fmt.Sprintf("%-98s", text)
```

输出：
```
格式化后字节长度: 101
格式化后显示宽度: 99
```

啊！**格式化后是 101 字节**，不是 98 字节！

这说明：
- 原文本 91 字节
- 格式化后 101 字节
- 说明 fmt.Sprintf 没有截断，而是返回了更长的字符串？

让我查阅 Go 文档...

**fmt.Sprintf("%-98s", text) 的行为**：
- `s`：字符串
- `-`：左对齐
- `98`：最小宽度，**不是最大宽度**

如果字符串的**字节长度** < 98，补空格到 98
如果字符串的**字节长度** ≥ 98，**不截断**，返回原字符串

我们的文本 91 字节 < 98 字节，所以：
- 应该补 7 个空格
- 结果应该是 98 字节

但实际是 101 字节？

**可能的原因**：文本实际上不是 91 字节？

让我数一下...

```go
text := "🌲 Render: Component functions called to generate new VNode trees based on current state."
```

- 🌲 emoji 在 UTF-8 中占用 4 字节
- 其余 ASCII 字符每个占 1 字节
- 总共 88 runes
- 如果 emoji 是 4 字节，其余 87 ASCII 是 87 字节
- 总计：4 + 87 = 91 字节 ✅

那为什么格式化后是 101 字节？

**答案**：fmt.Sprintf 的宽度参数指的是**字符数**（rune count），不是字节数！

- 文本有 88 runes
- `%-98s` 要求至少 98 个字符（rune）
- 所以补 10 个空格（不是 7 个）
- 结果：88 + 10 = 98 个字符（rune）
- 但是这些字符的字节长度：
  - 87 ASCII = 87 字节
  - 1 emoji (🌲) = 4 字节
  - 10 空格 = 10 字节
  - 总计：87 + 4 + 10 = 101 字节 ✅

**显示宽度**：
- 87 ASCII = 87 位置
- 1 emoji = 2 位置
- 10 空格 = 10 位置
- 总计：87 + 2 + 10 = 99 位置 ✅

**可用宽度**：98 位置（100 屏幕 - 2 边框）

**结论**：99 > 98，溢出 1 个位置！✓

---

## 问题总结

```
屏幕宽度: 100 位置
左边框  : 1 位置 (│)
右边框  : 1 位置 (│)
可用宽度: 98 位置

文本显示宽度:
  87 ASCII字符  = 87 位置
 + 1 emoji (🌲)  =  2 位置
 + 10 填充空格    = 10 位置
───────────────────────────
  总计           = 99 位置

99 > 98 → 溢出 1 个位置！
```

## 为什么 fmt.Sprintf 会有这个问题？

### fmt.Sprintf 的宽度语义

```go
fmt.Sprintf("%98s", text)   // 按字符数（rune count），不是字节数
fmt.Sprintf("%98d", num)   // 按十进制数字的字符数
```

对于 `%s`：
- 宽度指的是**最小字符数**（rune count）
- 不是字节数
- 不是显示宽度（不考虑宽字符）

### 为什么会这样设计？

Go 的 fmt 包遵循 C 语言 printf 的传统：
- 历史上，ASCII 字符只占 1 字节
- 字符数 = 字节数 = 显示宽度
- 不需要考虑宽字符（emoji、中文等）

现代应用中：
- UTF-8 编码：1 个字符（rune）可能占 1-4 字节
- 显示宽度：1 个字符（rune）可能占 1-2 个显示位置
- 字符数 ≠ 字节数 ≠ 显示宽度

## 正确的解决方案

### 方案 1：不使用格式化（推荐）

```go
// ✅ 让 Bordered 组件自动处理
content := app.NewTextBuilder(text).Build()
```

**优点**：
- 简单
- Bordered 组件会自动适应内容宽度
- 不会溢出

### 方案 2：限制显示宽度

```go
// ✅ 使用 runewidth 截断
import "github.com/mattn/go-runewidth"

maxWidth := 96  // 100 屏幕 - 2 边框 - 2 余量
truncated := runewidth.Truncate(text, maxWidth)
content := app.NewTextBuilder(truncated).Build()
```

### 方案 3：简化文本（我们的方案）

```go
// ✅ 确保文本足够短
explanations := map[string]string{
    "Render": "Component functions called to generate VNode trees from state.",  // 62 字符
}
```

## 关键要点

1. ❌ **不要**用 `fmt.Sprintf` 来控制终端文本宽度
2. ❌ **不要**假设字符数 = 显示宽度
3. ✅ **使用** `runewidth.StringWidth()` 计算显示宽度
4. ✅ **使用** `runewidth.Truncate()` 截断文本
5. ✅ **简化** 文本避免溢出

## 其他受影响的地方

任何使用以下模式的代码都可能有问题：

```go
// ❌ 危险
fmt.Sprintf("%-50s", text)   // 可能溢出
fmt.Sprintf("%50s", text)    // 可能溢出

// ✅ 安全
runewidth.Truncate(text, 50) // 正确截断
runewidth.StringWidth(text)  // 正确计算宽度
```
