# Pixel 图表渲染的性能影响、优化手段与验证计划

## 1. 目的

`PIXEL_CHART_RENDERING_ARCHITECTURE.md` 和 `CURRENT_SYSTEM_IMPACT_AND_FEASIBILITY_REVIEW.md`
已经说明了：

- 为什么当前系统不能直接支持图片像素图表
- 方案会冲击哪些现有层
- 应如何做最小可行性验证

本文件进一步补足“性能”这一维度，回答三个问题：

1. 如果采用像素化渲染，性能问题具体体现在哪里
2. 这些性能问题应该如何解决与优化
3. 应该怎样验证优化是否真的有效，而不是主观感觉更快

## 2. 性能问题的来源

当前系统的性能优化方向是：

- 文本缓冲
- line diff
- run merging
- dirty rect hint
- 光标最小移动

相关实现主要集中在：

- `framework/app.go`
- `runtime/paint/renderer.go`
- `runtime/paint/buffer.go`

这意味着当前系统擅长的是：

> 只输出少量变化的字符内容

而像素图表会把工作模式改成：

> 先 rasterize 位图，再上传或输出图像

因此性能问题通常来自五个方面。

### 2.1 CPU 开销增加

文本图表的 CPU 成本主要是：

- 数据采样
- 字符映射
- 文本缓冲写入
- 文本 diff

像素图表会额外增加：

- 离屏 rasterize
- 抗锯齿或像素合成
- 文本标签绘制到位图
- 图像编码或协议封装
- 图像缓存命中判断

### 2.2 输出带宽增加

当前 line diff 可以把一次更新压缩到少数变化行。

而图像路径如果没有区域级更新，通常会变成：

- 重新生成整图
- 重新发送整图

这会显著提高：

- 终端输出字节数
- 远程连接带宽消耗
- 每帧传输时延

### 2.3 内存占用增加

像素模式通常需要额外持有：

- 原始 bitmap
- 编码后图像数据
- 图层缓存
- tile 或 dirty region 缓存
- 静态层 / 动态层副本

这与当前 `paint.Buffer` 的文本 cell 模型相比，内存增长会更明显。

### 2.4 既有文本优化失效

当前优化依赖：

- 文本行 hash
- 文本行 diff
- 相同样式 run 合并

这些优化在图像路径下很难直接复用。

如果没有单独的图像 diff 策略，就会出现：

- 小变化导致整图重绘
- 小变化导致整图重传

### 2.5 resize 与高频刷新成本上升

文本模式下 resize 的主要成本是：

- 重新布局
- 重新写字符缓冲

图像模式下 resize 还会额外触发：

- 重新计算 pixel rect
- 重新 rasterize
- 重新编码
- 重新上传

在实时图表和 streaming 场景里，这个成本尤其明显。

## 3. 哪些场景性能风险最高

### 3.1 高频更新图表

例如：

- 实时 `linechart`
- 高频 `heatmap`
- 带成交量的 `candlestick`

如果每次更新都整图 rasterize + 整图上传，性能很容易不可接受。

### 3.2 多图并排页面

例如：

- dashboard
- gallery
- 多个 mini chart 同屏

此时即使单图成本可接受，总成本也会叠加。

### 3.3 远程终端或协议支持较差环境

例如：

- SSH
- tmux
- CI 环境
- 对图形协议支持不完整的终端

这类环境下，图像路径的带宽和稳定性风险都更大。

## 4. 性能优化策略

性能问题不是只能“接受变慢”，而是必须配套优化。

以下优化建议按优先级排序。

### 4.1 只在明确需要时启用 image mode

不要默认所有图表都走像素渲染。

建议引入明确策略：

- `Auto`
- `TextOnly`
- `ImageOnly`

并且 `Auto` 应满足：

- 终端明确支持图像协议
- 图表类型确实受益明显
- 页面不是高频多图场景

否则就继续走文本路径。

### 4.2 引入静态层 / 动态层拆分

图表中的很多内容并不会每帧变化。

建议拆成：

- 静态层
  - 坐标轴
  - 标题
  - 网格
  - legend
  - 背景
- 动态层
  - 折线
  - 点位
  - 热度矩阵
  - 成交量柱

优化效果：

- 静态层只生成一次
- 动态层按数据变化局部刷新
- resize 才整体失效

### 4.3 引入区域级更新

不能接受“任何变化都整图重传”。

建议优先支持：

- dirty rect
- tile 更新
- 区域 hash

也就是说：

- 只重绘有变化的区域
- 只重新编码有变化的 tile
- 只上传有变化的区域

这一步是像素图表性能能否成立的关键。

### 4.4 引入图像对象缓存

建议至少缓存三类对象：

- 原始 raster 结果
- 编码后的协议 payload
- 终端图像对象 ID 与 placement 信息

缓存键建议包含：

- chart type
- size
- theme
- data hash
- static layer hash
- graphics mode

没有这层缓存，性能会反复消耗在重复编码和重复上传上。

### 4.5 高频场景节流

对于 streaming chart，建议 image mode 下单独节流，不要沿用文本刷新频率。

推荐做法：

- 图像图表独立帧率上限
- 高频数据先聚合后再重绘
- 对用户不可感知的中间帧直接丢弃

例如：

- 文本路径允许更高频响应
- 图像路径限制到较低稳定 FPS

### 4.6 分级回退

性能优化不应只靠“继续优化 image mode”，也要允许主动退回文本模式。

建议建立自动退回条件：

- 输出字节数持续过高
- 终端协议不稳定
- 帧时间超阈值
- 连续 cache miss

回退顺序建议：

1. Image
2. Braille / Block
3. ASCII

### 4.7 先支持少量图表，不同时铺开

从性能角度，不建议一开始让所有图表支持 image mode。

建议顺序：

1. `linechart`
2. `heatmap`
3. `scatterplot`
4. `candlestick`

这样可以：

- 控制实现面
- 控制缓存复杂度
- 控制回归成本

## 5. 对当前系统的具体优化要求

### 5.1 `framework.App`

优化重点：

- 不要在 `App.render()` 内直接拼协议输出
- 先把“文本帧”和“图像帧”组织成统一的 scene/frame
- 异步渲染时必须把图像提交纳入同一帧边界

否则风险是：

- 文本和图像不同步
- 闪烁
- 图层顺序错乱

第一阶段建议再明确一条策略：

- 含 image layer 的实验帧优先走同步提交
- 不要在 capability、scene 和 prototype 都未稳定前，就把图像路径强塞进 `AsyncRenderer`

### 5.2 `runtime/paint.Renderer`

优化重点：

- 不把图像路径强塞进现有 line diff 逻辑
- 新增 image-aware render backend 或 scene compositor
- 保留文本 renderer 作为 fallback 和主力路径

当前 line diff renderer 应继续服务文本层，而不是承担所有图像逻辑。

### 5.3 `runtime/platform`

优化重点：

- 图形协议适配层独立
- 图像对象复用能力
- 输出节流和批量提交

不要把 Kitty/Sixel 细节泄漏到 chart 组件或 `App.render()`。

### 5.4 `testing`

优化重点：

- 文本回归继续保留
- 图像路径增加专门 benchmark 和 golden
- diagnostics 能输出：
  - bitmap
  - tile hash
  - region 更新信息

否则性能问题很难客观定位。

## 6. 需要采集的性能指标

如果不定义指标，后面就无法判断优化是否有效。

建议至少采集：

### 6.1 渲染时间

- 首帧时间
- 普通更新帧时间
- resize 后首帧时间
- 高频更新下平均帧时间

### 6.2 输出量

- 每帧输出字节数
- 平均输出字节数
- 峰值输出字节数

### 6.3 缓存指标

- 静态层命中率
- 图像 payload 命中率
- tile 命中率
- cache miss 后的恢复成本

### 6.4 资源占用

- CPU 占用
- 内存占用
- 图像缓存占用

### 6.5 稳定性指标

- 连续 resize 后是否错位
- 多次切换 alternate screen 后是否残留图像
- 非支持终端是否正确回退

## 7. 建议的 benchmark 设计

### 7.1 文本模式基线

先记录当前文本图表的基线性能：

- `linechart`
- `heatmap`
- `scatterplot`

尺寸建议固定几档：

- 小图
- 中图
- 大图

### 7.2 单图 image prototype benchmark

第一批只 benchmark `linechart image prototype`。

建议测：

- 静态首帧
- 单点更新
- 整段数据更新
- resize

### 7.3 多图页面 benchmark

模拟 dashboard：

- 1 张主图
- 4 张小图
- 8 张小图

比较：

- 文本模式
- image mode
- mixed mode

### 7.4 远程 / 慢速环境 benchmark

如果最终目标包含 SSH / tmux，需要额外测：

- 输出字节数
- 重绘时间
- fallback 切换行为

## 8. 建议的性能止损条件

为了避免 image mode 方案无限扩张，建议提前定义止损标准。

例如：

- 某类图表 image mode 平均帧时间超过文本模式若干倍且收益有限
- 高频更新场景无法通过缓存和区域更新把帧时间压回可接受范围
- 输出字节数在多图场景下持续不可控
- 主线调试和测试成本显著恶化

出现这些情况时，应当：

- 将 image mode 保持为实验性能力
- 或仅限少数场景启用
- 不强推成全局默认路径

## 9. 推荐的落地顺序

从性能角度，最稳的顺序是：

1. 先测当前文本路径基线
2. 再做单图 `linechart image prototype`
3. 先实现静态层缓存
4. 再做区域级更新
5. 最后再尝试多图与高频刷新

不要一开始就：

- 多图同屏
- 高频 streaming
- 多协议兼容

否则很难分辨到底是哪一层拖慢了系统。

## 10. 最终结论

采用像素化渲染后，性能问题主要集中在：

- CPU
- 输出带宽
- 内存
- 既有文本 diff 优势失效
- resize 与高频刷新成本上升

但这些问题不是无法管理，而是必须依赖系统级优化：

- 明确启用条件
- 静态层 / 动态层拆分
- 区域级更新
- 图像对象缓存
- 高频节流
- 自动回退

一句话总结：

**像素图表的性能问题，不在“能不能画”，而在“能不能避免每次都整图重 rasterize + 整图重上传”。**
