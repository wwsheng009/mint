# Mint UI 项目实施质量审查 Prompt

**版本**: v1.0
**日期**: 2026-01-31
**用途**: 指导 AI 或审查人员对项目实施质量进行系统性审查

---

## 使用说明

将以下 Prompt 提供给 AI，可对 Mint UI 声明式架构的实施质量进行全面审查。

---

## 一、完整审查 Prompt

```
你是一位资深的 Go 语言架构师和代码审查专家。请对 Mint UI 声明式架构项目的实施质量进行全面审查。

## 项目背景

Mint UI 是一个现代 Go TUI (终端用户界面) 框架，正在从命令式架构迁移到声明式架构，采用 React-like 的 VNode + Fiber + Hooks 范式。

## 审查范围

请从以下维度进行审查：

### 1. 架构一致性审查

检查实现是否符合设计文档：
- 对照 `SYSTEM_ARCHITECTURE.md` 检查核心架构实现
- 对照 `API_DESIGN.md` 检查 API 设计一致性
- 对照 `DIRECTORY_STRUCTURE.md` 检查目录结构
- 验证分层原则：Application → SDK → Framework → Runtime → Platform

**审查要点**：
- [ ] VNode 接口是否完整实现？
- [ ] Fiber 节点结构是否符合设计？
- [ ] Reconciler (Diff) 算法是否正确？
- [ ] Hooks 系统是否符合调用规则？
- [ ] 渲染管线 (DrawCmd → Buffer → ANSI) 是否完整？

### 2. 代码质量审查

检查代码质量和规范：

**命名规范**：
- [ ] 文件命名是否使用 snake_case？
- [ ] 接口命名是否使用 Capability + able 后缀？（如 Measurable, Paintable）
- [ ] 常量命名是否使用 PascalCase 或 UPPER_SNAKE_CASE？

**代码结构**：
- [ ] 包结构是否清晰？
- [ ] 循环依赖是否避免？
- [ ] 公开 API 是否有完整的 godoc 注释？

**错误处理**：
- [ ] 错误是否被正确处理而非忽略？
- [ ] 错误是否包含上下文信息？
- [ ] 是否使用 fmt.Errorf("context: %w", err) 包装错误？

### 3. Hooks 实现审查

重点检查 Hooks 系统：

**运行时验证**（参考 SYSTEM_ARCHITECTURE.md 1.3 节）：
- [ ] HookValidator 是否实现？
- [ ] 是否检查 Hooks 调用顺序一致性？
- [ ] 是否检查 Hooks 数量一致性？
- [ ] 是否检查 Hooks 类型一致性？
- [ ] 错误信息是否包含修复建议？

**useState 实现**：
- [ ] 状态更新是否触发重新渲染？
- [ ] 是否支持类型安全版本（UseStateInt, UseStateString 等）？

**useEffect 实现**：
- [ ] 依赖数组比较是否正确？
- [ ] 清理函数是否在卸载时执行？
- [ ] 空依赖是否只执行一次？

### 4. 状态系统审查

检查状态管理（参考 API_DESIGN.md 5.2 节）：

**useState vs ReactiveStore 分工**：
- [ ] useState 是否仅用于组件本地状态？
- [ ] ReactiveStore 是否用于全局/跨组件状态？
- [ ] 是否有混用的反模式？

**状态不变性**：
- [ ] 状态是否可枚举、可快照？
- [ ] 是否避免隐式全局状态？

### 5. 布局系统审查

检查布局实现（参考 GRID_LAYOUT_DESIGN.md）：

**容错机制**：
- [ ] 越界是否有自动修复（Clamp 模式）？
- [ ] 重叠是否有检测和处理？
- [ ] 错误是否有可视化提示（开发模式）？

**布局算法**：
- [ ] Fixed/Flex/Auto 尺寸计算是否正确？
- [ ] 跨行跨列是否正确处理？

### 6. 性能审查

对照 BENCHMARK.md 检查性能：

**基准测试**：
- [ ] 是否有完整的基准测试套件？
- [ ] 渲染性能是否达标（≥ 60 FPS）？
- [ ] 布局计算是否达标（< 1ms）？
- [ ] Diff 算法是否达标（1000 节点 < 5ms）？

**优化措施**：
- [ ] 是否实现 Dirty Region 跟踪？
- [ ] 是否实现 Style Diff 优化？
- [ ] 是否支持虚拟化渲染？

### 7. 测试覆盖审查

检查测试质量：

**覆盖率**：
- [ ] 核心模块测试覆盖率是否 ≥ 80%？
- [ ] 边界情况是否有测试？
- [ ] 错误路径是否有测试？

**测试类型**：
- [ ] 单元测试是否完整？
- [ ] 集成测试是否覆盖关键流程？
- [ ] 性能基准测试是否存在？

### 8. 文档一致性审查

检查文档与实现的一致性：

- [ ] API 文档是否与实现一致？
- [ ] 示例代码是否可运行？
- [ ] 迁移指南是否准确？
```

## 二、分项审查 Prompt

### 2.1 架构审查 Prompt

```
请对 Mint UI 项目的架构实现进行审查。

重点检查：
1. VNode 系统是否完整实现 VNode 接口（Type, Props, Children, Key）
2. Fiber 节点是否包含必要字段（Return, Child, Sibling, EffectTag）
3. Reconciler 是否正确实现 Diff 算法
4. 分层是否清晰（Runtime 不依赖 Framework）

对照 SYSTEM_ARCHITECTURE.md 进行检查，列出不一致之处。
```

### 2.2 Hooks 审查 Prompt

```
请对 Mint UI 项目的 Hooks 实现进行审查。

重点检查：
1. 运行时验证器 HookValidator 是否实现
2. useState 状态更新是否触发重新渲染
3. useEffect 依赖比较和清理函数是否正确
4. useMemo/useCallback 缓存是否生效
5. 错误信息是否友好并包含修复建议

对照 SYSTEM_ARCHITECTURE.md 第 1.3 节进行检查。
```

### 2.3 性能审查 Prompt

```
请对 Mint UI 项目的性能实现进行审查。

重点检查：
1. 是否有基准测试套件
2. 渲染帧率是否 ≥ 60 FPS
3. 布局计算是否 < 1ms
4. Diff 算法是否 < 5ms (1000 节点)
5. 是否实现 Dirty Region 跟踪
6. 是否实现 Style Diff 优化

对照 BENCHMARK.md 进行检查，列出未达标项。
```

### 2.4 代码质量审查 Prompt

```
请对 Mint UI 项目的代码质量进行审查。

重点检查：
1. 命名规范（文件 snake_case，接口 XxxAble）
2. 包结构和依赖关系
3. 错误处理是否完整
4. godoc 注释是否完善
5. 是否存在代码坏味道（过长函数、重复代码等）

请列出具体的问题位置和改进建议。
```

### 2.5 测试覆盖审查 Prompt

```
请对 Mint UI 项目的测试覆盖进行审查。

重点检查：
1. 核心模块测试覆盖率是否 ≥ 80%
2. 边界情况是否有测试
3. 错误路径是否有测试
4. 是否有集成测试
5. 是否有性能基准测试

运行以下命令获取覆盖率：
go test ./... -coverprofile=coverage.out
go tool cover -func=coverage.out

请列出覆盖不足的模块和建议。
```

## 六、常见问题检查清单

### 6.1 Hooks 常见问题

```
□ Hooks 是否在条件语句中调用？（不允许）
□ Hooks 是否在循环中调用？（不允许）
□ Hooks 调用顺序是否每次渲染一致？
□ useEffect 依赖数组是否完整？
□ useEffect 清理函数是否返回？
□ useMemo/useCallback 依赖是否正确？
```

### 6.2 性能常见问题

```
□ 是否有不必要的重新渲染？
□ 是否有内存泄漏（Effect 未清理）？
□ 是否有过深的组件嵌套？
□ 大列表是否使用虚拟化？
□ 是否有昂贵的计算未缓存？
```

### 6.3 状态管理常见问题

```
□ 是否有全局状态放入 useState？
□ 是否有本地状态放入 ReactiveStore？
□ 状态更新是否导致不必要的重新渲染？
□ 是否有状态突变（mutation）？
```
